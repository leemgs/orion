# CPU 메모리 계층 레짐 프로브 — 실측 결과

`experiments/cpu_hierarchy_probe.py` 로 이 실행 환경의 **실제 CPU**에서
측정한 데이터입니다. 시뮬레이션·합성·모델링이 아니라 `time.perf_counter_ns`
기반 실측입니다.

## 무엇을 측정했나

- **플랫폼:** Intel Xeon @ 2.80 GHz, L2 4 MiB, **L3(LLC) 33 MiB**, DRAM 15 GiB
  (이 컨테이너에 실재하는 하드웨어).
- **방법:** 단일 사이클 순열 포인터 체이싱(데이터 의존 접근)으로 하드웨어
  프리페처를 무력화하고, 작업집합 W 를 0.5 MiB → 256 MiB 로 스윕하며
  접근당 지연을 측정. `R_C = C_fast(=33 MiB) / W`.

## 결과 (실측)

| 구간 | 접근당 지연 |
|------|-------------|
| 캐시 상주 (W ≤ 1 MiB) | **84.1 ns** |
| DRAM 바운드 (W ≥ 128 MiB) | **185.1 ns** |
| **계단 배수** | **2.20×** |

W 가 빠른 메모리 용량을 넘어서면(R_C 감소) 지연이 계단식으로 증가한다는
논문의 **capacity-limited 레짐 전환**이 실리콘에서 관측됨.

## 정직한 한계 (반드시 함께 읽을 것)

1. **1개 플랫폼(CPU 캐시 계층)의 정성적 검증**이다. 논문이 주장하는
   A100·TPU v4·Inferentia2·MI250·Optane **5개 가속기의 정량 데이터가 아니다.**
2. Python hop당 상수 오버헤드(~80 ns)가 섞여 전환의 날카로움이 하드웨어
   실제보다 완만하다. C/ctypes 마이크로벤치로 재구현하면 더 선명해진다.
3. 이 데이터로는 논문의 θ_B, 전략 역전 크기(±%), 분류기 정확도 등
   **가속기 정량 수치를 대체할 수 없다.** 그 값들은 실제 가속기 계측
   campaign 이 필요하다 (`paper/submission/code_paper_reconciliation.md` 참조).
